# UI Mockup — Combat Screen

ASCII-мокапы боевого экрана для трёх размеров терминала и двух локалей.
Сцена — бой 1 сценария «Hollow Oak Mine / Шахта Гнилого Дуба»: PC Aelar
(воин, 1 уровень) против двух гоблинов в главном туннеле.

Нотация:
- `@` — Aelar (PC, color token `pc-fg`).
- `g` — Goblin (enemy, `enemy-fg`).
- `d` — друидский пёс-союзник (friendly, `friendly-fg`) — используется
  только в Разделе B, чтобы показать клетку с несколькими существами.
- `#` — стена (`wall-fg`).
- `,` — труднопроходимая (`difficult` terrain, `dim-fg`).
- `o` — сундук (`object-fg`).
- `.` — пол (нейтральный).
- `▶` — маркер текущей очереди в INITIATIVE.
- `═║╔╗╚╝` — двойные рамки для секций.
- `─│┌┐└┘├┤┬┴┼` — одинарные рамки внутри панелей и сетки.
- `░▒▓` — заливка (movement range / target zone / highlights).
- Размер «зум small» — 1 клетка = 1 ячейка терминала. «medium» — 3×3.
  «large» — 5×3.
- Все мокапы — точные по символам внутри код-блоков. Эмодзи запрещены.
- Цветовых ANSI-кодов нет. После каждого мокапа — таблица цветовых
  токенов для CSS Textual.

## Открытые вопросы (для архитектора)

1. **Stack digit colour.** В B.2/B.3 при стеке PC+союзник цифру «2»
   рисуем в `pc-fg` или в `friendly-fg`? Сейчас в мокапе принят `pc-fg`,
   потому что доминирует приоритет PC. Если стек PC+враг — нужен
   отдельный токен (`mixed-fg`) или это запрещённая комбинация (враг и
   PC не могут стоять на одной клетке, кроме как через эффект).

2. **Cursor highlight on color theme.** В тексте использован `[░]` как
   универсальный маркер. На `color.tcss` это может быть inverse video
   вместо `[░]`. Решение архитектора: дублируем оба механизма (символ +
   цвет) или только цвет, оставляя символ для `monochrome` / `--ascii-only`?

3. **Diagonal path arrows.** Сейчас в large-зуме диагональ пути я
   обозначил `\\\` / `///`. Это занимает 3 ячейки и плохо читается
   рядом с другими символами. Альтернатива — выделить ВСЮ клетку
   подсветкой `░░░` + поставить одну стрелку в углу. Какой вариант
   выбрать?

4. **Status indicator scheme** (C.3). Сейчас короткие двух-буквенные
   коды (`Po`, `Pr`, `Sn`). Для русской локали они **не локализованы**
   (`Po` остаётся `Po`, не `От` от «Отравлен»). Это снижает порог
   когнитивной нагрузки (одни и те же коды на обоих языках), но может
   быть нелогично для рускоговорящего игрока. Локализовать индикаторы
   (на русском `От` / `Ле` / `Ош`) или оставить ENG-сокращения?

5. **Sprite for downed creature** (C.2 Frame 3, C.7 после боя). YAML
   спрайта позволяет `char_dead: x` (1×1). В medium-зуме мы рисуем
   3-строчную «решётку» из X (`,X,/oXo/X\`) — это нестандартное
   расширение спрайт-системы. Либо вводим поле `sprite_medium_dead` /
   `sprite_large_dead`, либо автоматически заменяем буквы спрайта на `X`
   программно. Что предпочтительнее?
