# ADR 0001 — Гексагональная архитектура и SQLite через Repository

## Контекст

Требования (`req.md`) обязывают:
- следовать SOLID;
- использовать SQLite;
- взаимодействовать с БД через паттерн Repository;
- иметь возможность гибко конфигурировать и **легко добавлять контент**
  (расы, классы, предметы, локации).

Цели проекта (`docs/DESIGN.md`) дополнительно требуют:
- два разных интерфейса поверх одного и того же ядра (классический CLI и
  ретро-TUI 80–90х);
- высокую тестируемость (фиксированный RNG, in-memory подмена БД);
- расширение системы через данные (YAML/JSON), а не код.

## Решение

Применяем **гексагональную архитектуру** (Ports & Adapters) с четырьмя слоями:

- `domain/` — чистая модель правил D&D 5e; без I/O.
- `application/` — use-cases и **порты** (Protocol/ABC).
- `infrastructure/` — реализации портов (SQLite, YAML, RNG, ИИ-стратегии).
- `interfaces/` — пользовательские адаптеры (Typer CLI, Textual TUI).

Зависимости направлены внутрь: `interfaces → application → domain`.
`infrastructure` подключается через DI в композиционном корне (CLI `main`).

SQLite — единственное хранилище. Доступ — только через интерфейсы-репозитории
из `application/ports/`. Контент (расы/классы/предметы/монстры/сценарии)
поставляется в `content/` как YAML и загружается в БД сидером.

## Последствия

**Плюсы:**
- ядро правил тестируется без БД и UI;
- два UI поверх одного движка — без дублирования;
- замена SQLite на любое другое хранилище — заменой одной реализации;
- добавление расы/класса — это новый YAML и (по необходимости) плагин-класс
  для особенности, ядро не правится;
- студенту видны конкретные SOLID и паттерны в работе.

**Минусы:**
- больше файлов и слоёв, чем у наивного «всё в одном модуле»;
- требует дисциплины DI (передавать зависимости, а не импортировать).

## Альтернативы и почему отвергнуты

- **Монолит со SQLAlchemy ORM**: ORM скрыл бы паттерн Repository, который явно
  требуется заданием; «всё в одном модуле» затрудняет тесты и второй UI.
- **Event-sourcing**: избыточно для учебного проекта.
- **MVC по слою UI**: достаточно для одного UI, но второй UI не разделяет
  модель чисто — выбираем гексагональный подход.
