# OPEN_QUESTIONS — принятые решения и оставшиеся вопросы

Все решения фиксируются здесь, а потом разъезжаются по соответствующим
design-документам. Когда вопрос закрыт — он остаётся в файле с пометкой
**ЗАКРЫТО** и кратким резюме, чтобы потом не возвращаться.

---

## ✅ Q1. Сетка боя — **квадраты**

Решение архитектора: **квадратная сетка**, 1 клетка = 5 футов. Стандарт
правил книги, проще и красивее в ASCII, лаконичнее в коде.

**Дополнительно:**
- Несколько существ могут стоять на одной клетке (нет жёсткого
  ограничения; в UI помечаем стоп-маркером «несколько»).
- Соседство по 8 направлениям (4 ортогональных + 4 диагональных).
- Дистанция по правилам книги: каждая клетка 5 футов, включая
  диагонали (Chebyshev). Если в будущем понадобится «1-2-1» правило
  старых редакций — это переключаемая стратегия.

**Затронуто:** `ENGINE.md` (раздел 2), `UI.md` (рендер карты).

## ✅ Q3. 2 расы и 2 класса для MVP — **Человек + Эльф / Воин + Плут**

Воин — самый простой класс правилами. Плут даёт Скрытность, Скрытую атаку,
обнаружение ловушек — отлично подходит сценарию-демо (альтернативные пути,
скрытые комнаты). Волшебник — пост-MVP (заклинания дорого моделировать).

Подклассы (1-й подкласс на класс в MVP):
- Воин → **Чемпион** (Champion).
- Плут → **Вор** (Thief, без заклинаний — Мистический ловкач отложен).

**Затронуто:** `content/core/classes/` и `content/core/species/`.

## ✅ Q6. Многопользовательский режим — **сейчас только hot-seat (заложить минимум)**

- **Сейчас:** один игрок, один персонаж.
- **Hot-seat** заложен в дизайне (передача управления между PC при их
  ходе, общий экран, возможность посмотреть лист товарища между ходами).
- **Live-мастер** и **сеть** — **не закладываем интерфейсы сейчас**.
  Принцип: пишем чистое ядро, чтобы потом эти направления добавились
  **без ломающих изменений**. Подробности в `MASTER.md` и
  `ROADMAP.md`.

**Конкретные инварианты, которые нельзя нарушать сейчас**, чтобы не
заблокировать будущие направления:
1. Все интенты и события — DTO (pydantic), сериализуемые в JSON.
2. `EventBus` — единственный канал событий движка наружу.
3. RNG — порт; ни одно правило не вызывает `random.*` напрямую.
4. UI и БД — за портами. Domain не знает про них.

**Затронуто:** `ROADMAP.md`, `ARCHITECTURE.md`, `MASTER.md`.

## ✅ Q9. Темы оформления — **две: «color» (цветная, по умолчанию) и «monochrome»**

«Color» — основная, красивая, ретро-палитра (тёмный фон, акценты по
семантике — союзник/враг/предмет/эффект). «Monochrome» — чёрно-белая
для скриншотов/принтскринов и старых терминалов. Все остальные темы
(phosphor/amber/vga-16) — на потом, добавятся как CSS-варианты при
желании, без правок кода.

**Затронуто:** `UI.md`.

## ✅ Q11. Куда писать БД и контент — **`platformdirs` + флаг `--workdir`**

- БД: `~/.local/share/dnd/dnd.sqlite`

## ✅ Q12. Изменение сценария при наличии сейва — **запрещено**

При попытке отредактировать/перезагрузить сценарий, по которому есть
активные сейвы: UI/CLI сообщает «по сценарию X есть N сейвов, удалите
их или сделайте копию сценария» (`dnd content clone scenario:X --as Y`).
Сейв хранит `(scenario_id, scenario_version)`; при несовпадении версии —
блок загрузки.

В будущем — система миграций сценариев (раздел в `ROADMAP.md` под
открытым миром).

**Затронуто:** будущий `ContentService`, `SaveService`.

## ✅ Q13. Раскладка прав при live-мастере (пост-MVP) — **движок бросает, мастер может перебросить с пометкой**

Все броски делает движок (`RNG`). Мастер может:
- запросить переброс конкретного броска (`reroll`);
- переопределить результат (`set_result`);
- наложить преимущество/помеху на следующий бросок;
- изменить HP/состояние/позицию без броска;
- спавнить/удалять NPC;
- стартовать/завершать encounter.

Каждое вмешательство пишется в `GameLog` с тегом `master_intervention`
и причиной (мастер указывает причину текстом). Это даёт честный лог
для постфактум-разборок.

**Затронуто:** `MASTER.md`.

## Решения по итогам правок и аудита

Архитектор фиксированно сказал «иди по рекомендациям». Решения ниже —
закрытые ✅, можно ссылаться.

### ✅ Q14. Локализация контента — **inline-словарь**

`name: { en: "Goblin", ru: "Гоблин" }` в YAML, реализуется через
`LocStr` pydantic-обёртку (`translations: dict[str, str]` — открыта на
третий язык). Файлы остаются человеко-читаемыми, нет дубликатов.

**Затронуто:** `I18N.md` §4, формат YAML контента.

### ✅ Q15. Статистика бросков — **текущая сессия + за всё время по сейву**

- Среднее по **сырому d20** (без бонусов и преимущества/помехи).
- Окна: **текущая сессия** + дополнительный показатель «**за всё время
  по этому сейву**».
- **Мини-гистограмма** по граням 1..20.
- Место: вкладка **Journal** на листе персонажа + быстрая клавиша **`S`**
  в бою для оверлея.

**Затронуто:** `UI.md` §7, будущий `DiceStatisticsService`
(`application/engine/dice_stats.py`).

### ✅ Q16. Защита панели мастера в hot-seat — **PIN-код**

PIN хранится в `SaveMeta.master_pin_hash` (sha-256 + salt). При входе в
`MasterScreen` (`Ctrl+M`) — диалог PIN. Неверно → возврат в обычный UI.
Это пост-MVP, заложено заранее.

**Затронуто:** `MASTER.md` §5.2, `SaveService` (хранение хэша).

### ✅ Q17. Ввод бросков с настоящих кубиков — **флаг сценария**

`dice_input: live | computer` в YAML сценария. По умолчанию `computer`.
Режим `live` поднимает `LiveDiceRoller`, который запрашивает значение
у игрока через `UserInterface.request_dice_input(ctx)`. С мастером —
мастер видит ввод и может перебросить.

**Затронуто:** `MASTER.md`, `ENGINE.md` §7.5 (`LiveDiceRoller` —
пост-MVP).

### ✅ Q18. Hot-seat hand-off — **кнопка передачи**

`handover_mode: confirm` по умолчанию: после хода активного PC экран
показывает «Pass control to {next_player} — press ENTER». Авто-режим
доступен опционально (`handover_mode: auto`).

**Затронуто:** `UI.md` §8.

## Решения по итогам аудита 02 (контракты)

### ✅ Q19. RNG как driven-port — **`domain/ports/rng.py`**

Гексагональная нотация: driven-порт (правила «дёргают наружу») живёт в
`domain/`. Это устраняет нарушение `domain → application` (A-001).
Реализации остаются в `infrastructure/rng/`. Будет оформлено отдельным
**ADR-0003**.

**Затронуто:** `src/dnd/domain/ports/rng.py` (новый), импорт в
`domain/values/dice.py`, импорт в `infrastructure/rng/*.py`. Cleanup в
коммите C.

### ✅ Q20. `DiceExpr.roll()` напрямую vs `DiceRoller` — **конвенция, без линтера**

Низкоуровневый `DiceExpr.roll(rng)` остаётся доступным как
internal-helper для:

- генерации stats при создании персонажа (`CharacterBuilder`);
- внутренних unit-тестов домена;
- внутренней реализации `ComputerDiceRoller`.

**Правила движка** (`attack_roll`, `save`, `ability_check`,
`damage_roll`) — **только** через `DiceRoller`. Это закреплено
документацией в `ENGINE.md` §7.1 и проверяется на код-ревью; линтер-
правило (например, через AST-проверку) — пост-MVP, если будут срывы.

### ✅ Q21. `UserInterface` — **один порт сейчас**

Не разбиваем на `InputPort`/`OutputPort`/`ViewPort` в MVP. Если порт
начнёт распухать сверх ~12 методов или появится подсистема, которой нужен
только подмножество (например, `BattleViewPort` для отдельного процесса
рендеринга боя) — будем расщеплять. Сейчас 7 методов — терпимо.

**Затронуто:** `ARCHITECTURE.md` §3.3, `UI.md` §10.

### ✅ Q22. `MasterIntent` — **Tagged Union на pydantic v2**

`Annotated[RerollIntent | SetHpIntent | ..., Field(discriminator="kind")]`.
Каждая операция — отдельный pydantic-класс с типизированными полями;
mypy/IDE/валидация — полноценные.

**Затронуто:** `ENGINE.md` §6.1, `MASTER.md` §3 (источник истины),
будущий `application/dto/master_intent.py`.

### ✅ Q23. Регистрация плагинов — **явная в composition root**

`Registry.register("rage", RageFeature)` в `composition.py`, **не**
декораторы при импорте. Причина — декораторы создают скрытое глобальное
состояние и порядок-импортов-зависимую инициализацию.

`ContentService.validate()` при старте проверяет, что все `id` из
YAML, ссылающиеся на плагины, имеют зарегистрированные классы. Не
зарегистрировано — явная ошибка с указанием конкретного `id`.

**Затронуто:** `ARCHITECTURE.md` §1, §3.12; будущий `composition.py`.
