# OPEN_QUESTIONS — принятые решения и оставшиеся вопросы

Все решения фиксируются здесь, а потом разъезжаются по соответствующим
design-документам. Когда вопрос закрыт — он остаётся в файле с пометкой
**ЗАКРЫТО** и кратким резюме, чтобы потом не возвращаться.

## ✅ Q1. Сетка боя — **квадраты**

Решение архитектора: **квадратная сетка**, 1 клетка = 5 футов. Стандарт
правил книги, проще и красивее в ASCII, лаконичнее в коде.

**Дополнительно:**
- Несколько существ могут стоять на одной клетке (нет жёсткого
  ограничения; в UI помечаем стоп-маркером «несколько»).
- Соседство по 8 направлениям (4 ортогональных + 4 диагональных).
- Дистанция по правилам книги: каждая клетка 5 футов, включая
  диагонали (Chebyshev). Если в будущем понадобится «1-2-1» правило
  старых редакций — это переключаемая стратегия.

**Затронуто:** `ENGINE.md` (раздел 2), `UI.md` (рендер карты).

## ✅ Q6. Многопользовательский режим — **сейчас только hot-seat (заложить минимум)**

- **Сейчас:** один игрок, один персонаж.
- **Hot-seat** заложен в дизайне (передача управления между PC при их
  ходе, общий экран, возможность посмотреть лист товарища между ходами).
- **Live-мастер** и **сеть** — **не закладываем интерфейсы сейчас**.
  Принцип: пишем чистое ядро, чтобы потом эти направления добавились
  **без ломающих изменений**. Подробности в `MASTER.md` и
  `ROADMAP.md`.

**Конкретные инварианты, которые нельзя нарушать сейчас**, чтобы не
заблокировать будущие направления:
1. Все интенты и события — DTO (pydantic), сериализуемые в JSON.
2. `EventBus` — единственный канал событий движка наружу.
3. RNG — порт; ни одно правило не вызывает `random.*` напрямую.
4. UI и БД — за портами. Domain не знает про них.

**Затронуто:** `ROADMAP.md`, `ARCHITECTURE.md`, `MASTER.md`.

## ✅ Q9. Темы оформления — **две: «color» (цветная, по умолчанию) и «monochrome»**

«Color» — основная, красивая, ретро-палитра (тёмный фон, акценты по
семантике — союзник/враг/предмет/эффект). «Monochrome» — чёрно-белая
для скриншотов/принтскринов и старых терминалов. Все остальные темы
(phosphor/amber/vga-16) — на потом, добавятся как CSS-варианты при
желании, без правок кода.

**Затронуто:** `UI.md`.

## ✅ Q11. Куда писать БД и контент — **`platformdirs` + флаг `--workdir`**

- БД: `~/.local/share/dnd/dnd.sqlite`
- пользовательский контент: `~/.local/share/dnd/content/`
- конфиг: `~/.config/dnd/config.toml`
- логи: `~/.local/state/dnd/logs/`
- флаг `--workdir DIR` — перенести всё в `DIR/` (для разработки/учёбы).

## ✅ Q12. Изменение сценария при наличии сейва — **запрещено**

При попытке отредактировать/перезагрузить сценарий, по которому есть
активные сейвы: UI/CLI сообщает «по сценарию X есть N сейвов, удалите
их или сделайте копию сценария» (`dnd content clone scenario:X --as Y`).
Сейв хранит `(scenario_id, scenario_version)`; при несовпадении версии —
блок загрузки.

В будущем — система миграций сценариев (раздел в `ROADMAP.md` под
открытым миром).

**Затронуто:** будущий `ContentService`, `SaveService`.

## ✅ Q13. Раскладка прав при live-мастере (пост-MVP) — **движок бросает, мастер может перебросить с пометкой**

Все броски делает движок (`RNG`). Мастер может:
- запросить переброс конкретного броска (`reroll`);
- переопределить результат (`set_result`);
- наложить преимущество/помеху на следующий бросок;
- изменить HP/состояние/позицию без броска;
- спавнить/удалять NPC;
- стартовать/завершать encounter.

Каждое вмешательство пишется в `GameLog` с тегом `master_intervention`
и причиной (мастер указывает причину текстом). Это даёт честный лог
для постфактум-разборок.

**Затронуто:** `MASTER.md`.

## Новые вопросы по итогам правок

### Q14. Локализация контента — как маркировать поля

Контент в YAML содержит и **технические идентификаторы** (`id: goblin`),
и **локализуемые тексты** (имя, описание, броски диалогов). Варианты
хранения:

- **A. Параллельные поля:** `name_en`, `name_ru` в каждом объекте.
- **B. Отдельный bundle:** `goblin.yaml` хранит `id` и `name_key`,
  тексты — в `locales/en/monsters.yaml`, `locales/ru/monsters.yaml`.
- **C. Inline-словарь:** `name: { en: "Goblin", ru: "Гоблин" }`.

**Моя рекомендация: C** для лаконичности — оставляет файлы человеко-
читаемыми, не плодит дубликаты, легко добавить третий язык одной строкой.
B масштабируется лучше, но добавляет переключение контекста при
редактировании монстров.

**Нужно решение.** Если ответа нет — иду по C.

### Q15. Статистика бросков — что показываем

Решено вести среднее **сырых** d20-бросков без бонусов и без преимущества/
помехи. Открытые подвопросы:

- Какой объём окна для «сегодняшнего» среднего? Варианты: текущая
  сессия / последние N бросков (N=20) / последний игровой день в мире.
- Показывать ли распределение (мини-гистограмма)?
- Где в UI: в боковой панели всегда или по кнопке `S` (statistics)?

**Моя рекомендация:** окно — **текущая сессия**, доп. показатель
**«за всё время по этому сейву»**. Распределение — да, мини-гистограмма
по граням 1..20 (просто 20 столбцов высотой). Место — в листе персонажа
(вкладка «Журнал») + быстрая кнопка `S` в бою.

**Нужно решение** по объёму окна и месту в UI.

### Q16. Защита панели мастера в hot-seat

Решено: панель мастера приватная, другие игроки не должны видеть. В
одном устройстве это решается:

- **A. PIN-код мастера** при входе в панель.
- **B. Кнопка «передать мастеру»**, после которой UI блокирует ввод до
  ввода PIN.
- **C. Полностью отдельный режим запуска `dnd play --as-master`** в
  другом терминале.

**Моя рекомендация:** A для MVP+1 (когда добавим мастера). C — на потом,
когда появится сеть. PIN хранится в сейве (хэш).

**Нужно решение** (это пост-MVP, но удобно зафиксировать сейчас).

### Q17. Ввод бросков с настоящих кубиков — модель

Сейчас комп бросает. В будущем — режим «я брошу сам, введу значение».
Подвопросы:

- А что если игрок врёт? Мастер видит лог и решает; без мастера —
  игроку доверяем (это его игра).
- Без мастера, в соло — нужен ли этот режим вообще, или это только
  для игры за столом?

**Моя рекомендация:** режим включается флагом на уровне сценария
(`dice_input: live|computer`); без мастера он есть как «опция честности
игрока», с мастером — мастер видит ввод и может перебросить, если
заподозрит.

**Нужно решение**, но это пост-MVP.

### Q18. Hot-seat — момент передачи управления

Когда наступает ход PC игрока B, а до этого ходил PC игрока A:

- **A. Авто-переключение** — экран меняется на B сразу.
- **B. Кнопка «передать»** — A нажимает «передать ход», только тогда
  экран меняется.

**Моя рекомендация:** B — корректнее в реальной комнате (никто не
выхватывает клавиатуру). Между ходами можно смотреть листы товарищей,
но не делать действий за них.

**Нужно решение.** Это влияет на UI визард, но не критично — поведение
переключаемое через настройку.
