# MASTER — режим живого мастера (направление развития)

Документ описывает **киллер-фичу** проекта: режим, в котором за мастера
играет реальный человек. Это **направление развития**, а не задача MVP.
Здесь нет конкретных дат и спринтов — здесь описано, **как игра должна
быть устроена**, чтобы этот режим добавился без ломающих изменений.

> Принцип архитектора: «не закладываем интерфейсы сейчас, но
> разрабатываем так, чтобы потом всё подключилось без боли».

---

## 1. Зачем мастер

D&D — про коллективное воображение и спонтанные решения, которые
правила не покрывают. Сценарий-движок (наш `AutoGameMaster`) хорош для
демки, но настоящая игра живая: игроки придумывают план, который
сценарий не предусматривает, у героя есть личная история, мастер
вкидывает чит-моменты под обстоятельства.

Цель режима:

- **С мастером** — игра становится сессией настольной D&D, где
  приложение помогает: рисует карту, считает броски, держит инвентарь.
  Мастер занимается **историей**.
- **Без мастера** — игра проходится по предзаписанному сценарию,
  движок выступает в роли мастера-автомата.

Тот же сценарий, проигрываемый с живым мастером и без него, даёт разный
опыт: автомат предсказуем, мастер — нет.

---

## 2. Кто такой мастер в нашей модели

В `application/engine/players.py` (когда дойдём) появится:

```python
@dataclass
class Player:
    id: PlayerId
    nickname: str
    role: PlayerRole       # PARTICIPANT | MASTER | OBSERVER

class PlayerRole(StrEnum):
    PARTICIPANT = "participant"
    MASTER = "master"
    OBSERVER = "observer"
```

В MVP — один `Player` в роли `PARTICIPANT`. Мастер появляется при
добавлении hot-seat-master-режима: ещё один `Player` с
`role=MASTER`, разделяющий устройство.

## 3. Возможности мастера (чит-консоль)

Это **полный список** того, что мастер может сделать. Каждая операция —
отдельный pydantic-DTO, член discriminated union `MasterIntent` (см.
`ENGINE.md` §6.1). Имена DTO в коде — `RerollIntent`, `SetHpIntent`,
`SpawnCreatureIntent` и так далее.

**Этот раздел — единственный источник истины по списку операций.** В
`ENGINE.md` §6.1 ссылается сюда.

### 3.1 Кости и броски

| Операция | Смысл |
|---|---|
| `reroll(roll_id)` | Перебросить указанный бросок до момента его применения. |
| `set_roll(roll_id, raw)` | Жёстко задать «выпавшее» значение d20 (с пометкой в логе). |
| `grant_advantage(creature, next_n=1)` | Следующие N бросков существа — с преимуществом. |
| `grant_disadvantage(creature, next_n=1)` | То же, но с помехой. |
| `clear_pending_mods(creature)` | Сбросить накопленные модификаторы. |

### 3.2 Здоровье и состояния

| Операция | Смысл |
|---|---|
| `set_hp(creature, value)` | Прямая запись HP (включая 0 → бессознательный). |
| `deal_damage(creature, amount, type)` | Урон без атаки. |
| `heal(creature, amount)` | Лечение. |
| `apply_condition(creature, condition, duration?)` | Наложить состояние. |
| `remove_condition(creature, condition)` | Снять. |
| `revive(creature, hp=1)` | Поднять с 0 HP. |

### 3.3 Бой

| Операция | Смысл |
|---|---|
| `force_start_encounter(template, spawns)` | Стартовать бой не по сценарию. |
| `force_end_encounter(victor?)` | Завершить бой досрочно. |
| `set_initiative(creature, value)` | Подменить порядок инициативы. |
| `skip_turn(creature)` | Пропустить чей-то ход. |
| `extra_turn(creature)` | Дать существу дополнительный ход. |

### 3.4 Карта и существа

| Операция | Смысл |
|---|---|
| `spawn_creature(template, at)` | Поставить нового NPC. |
| `remove_creature(creature)` | Убрать (скрытно или с эффектом). |
| `move_creature(creature, to)` | Переставить по карте. |
| `change_terrain(square, kind)` | Изменить клетку (обрушить стену, открыть ловушку). |
| `set_light(area, level)` | Свет/тьма. |

### 3.5 Мир и сценарий

| Операция | Смысл |
|---|---|
| `set_flag(name, value)` | Подкрутить флаг мира. |
| `move_party(to_location)` | Телепортировать партию. |
| `give_item(character, item, qty=1)` | Положить предмет в инвентарь. |
| `take_item(character, item_id)` | Забрать. |
| `give_xp(character, amount, reason?)` | Начислить опыт (для геройства не по правилам). |
| `set_npc_disposition(npc, level)` | Перевод NPC из дружелюбного в враждебного и т.д. |
| `narrate(text, audience?)` | Вкинуть текст в лог (всем или конкретному игроку). |

### 3.6 Чит-вмешательство «по чувству»

Это **отдельный класс** действий — те самые «настольгические моменты»,
о которых говорил архитектор:

| Шаблон | Пример применения |
|---|---|
| «Герой боится воды» | мастер вешает на PC флаг страха, движок поднимает Сл. на спасбросок Мудрости от испуга. |
| «Это его родная деревня» | бонус-преимущество на проверки знания/убеждения с местными. |
| «Кинжал — память об отце» | модификатор +1 к атаке этим конкретным кинжалом, только в этой партии. |

Реализуется через `apply_modifier(target, modifier_spec)`:

```python
class Modifier(BaseModel):
    target_kind: Literal["creature", "item", "encounter"]
    target_id: str
    effect: dict          # +N к броску такого-то типа, преимущество и т.п.
    expires: dict | None  # "end_of_encounter", "end_of_day", "permanent"
    reason: str           # обязателен — мастер пишет «фамильный кинжал отца»
```

Лог получает запись `MasterModifierApplied(modifier, reason)`.

## 4. Инварианты

Чтобы мастер-режим работал прозрачно:

1. **Все вмешательства логируются.** В сейве остаётся след: кто, когда,
   что, зачем. Удалили сейв — потеряли историю. (Полностью согласуется с
   решением «история в сейве».)
2. **Игроки не видят вмешательств по умолчанию.** UI игрока показывает
   результат, как будто это сделал движок. Мастер видит честный лог.
3. **`master_transparency` — настройка сценария**:
   - `hidden` — стандарт. Игроки не знают о вмешательствах.
   - `tagged` — в логе игрока стоит пометка «*мастер*».
   - `full` — игрок видит причину вмешательства.
4. **Мастер не может вмешаться задним числом**: только до того, как
   событие «применилось» (см. `ENGINE.md` §6.2 про `RollIssued` →
   `RollApplied`). После применения — нужно явное «откатить» (это
   отдельный `MasterIntent`, не «незаметная» правка).
5. **Все вмешательства — детерминированы и сериализуемы.**
   `MasterIntent` — pydantic, JSON-сериализуем. Это даёт repro и сеть.

## 5. UI мастера (направление)

Не пишем сейчас. Описываю требования, чтобы потом не пересобирать.

### 5.1 Отдельная панель

`MasterScreen` — экран TUI, доступен **только** при `role=MASTER`. В нём:

- **Глобальный обзор:** карта боя со всеми статблоками NPC, инициатива,
  HP всех существ (включая PC, точно — не «оценочно»).
- **Чит-консоль:** меню операций из §3 с поиском и предпросмотром.
- **Журнал партии** с возможностью пометить любую запись «вмешательство».
- **Закулисы сценария:** дерево событий, флаги, цели; можно
  перепрыгнуть в любую точку.
- **NPC-контроль:** для каждого NPC — либо «ходит сам по `MonsterAI`»,
  либо «жду решения мастера» (мастер сам выбирает действие).
- **Заметки** — свободный блокнот мастера в сейве.

### 5.2 Приватность (hot-seat)

В hot-seat-режиме мастер сидит за тем же устройством, что игроки.
Защита:

- При входе в `MasterScreen` — PIN-код, заданный при создании партии.
- PIN хранится в сейве как **хэш** (sha-256 с salt).
- При неверном вводе — UI «дрожит» и возвращает в обычное меню.
- Если PIN не задан (один игрок, мастера нет) — экран мастера не
  доступен вообще.

### 5.3 Передача управления

В hot-seat вход в `MasterScreen` блокирует ввод обычных игроков и
выводит подсказку «передайте устройство мастеру». Выход — кнопка
«вернуть игрокам» (опц. с очищением экрана от чувствительной информации
на 1 сек, чтобы плечом не подсмотрели).

## 6. NPC: автоматический мастер vs живой

NPC ходят либо по `MonsterAI` (стратегии в `infrastructure/ai/`), либо
под управлением мастера.

```python
@dataclass
class NPCController:
    npc_id: CreatureId
    mode: Literal["ai", "manual", "scripted"]
    ai_strategy: str | None  # имя из MonsterAIRegistry
```

- `ai` — обычный авто-режим (для MVP).
- `manual` — мастер выбирает действие.
- `scripted` — сценарий заранее задал интент (например, в первый ход
  босс всегда кастует ритуал).

Переключение режима — это `MasterIntent: switch_npc_mode(npc, mode)`.
В MVP всегда `ai`.

## 7. AutoGameMaster и LiveGameMaster

Сейчас в коде есть `ScenarioRuntime`, который слушает события и
применяет триггеры сценария. Это и есть **автоматический мастер**.

Когда добавим живого:

```
ScenarioRuntime               (низкоуровневое — события в YAML-триггеры)
        ▲
        │ использует
        │
AutoGameMaster (текущий)    │  LiveGameMaster (будущий)
   реагирует автоматически  │  передаёт решения живому человеку через MasterUI
        ▲                   │       ▲
        └───────────────────┴───────┘
                  оба реализуют (будущий) GameMasterPort
                  ── порт пока НЕ создаётся, см. ниже ──
```

Сейчас порт `GameMasterPort` **не вводим** (по решению архитектора).
Уточнение терминологии: «не вводим порт» относится именно к
`GameMasterPort` — обратному каналу «движок → живой мастер». DTO
`MasterIntent` и метод `GameEngine.apply_master_intent` — это **прямой**
канал («команда сверху → движок»), они уже существуют и портом не
являются. См. `ROADMAP.md` §9 и `ENGINE.md` §6.4 для уточнения.

`ScenarioRuntime` пишем так, что в нём нет ничего, что бы мешало
обернуть его в порт потом.

Конкретно — `ScenarioRuntime`:
- слушает `EventBus`;
- читает сценарий и применяет триггеры через `GameEngine.apply_master_intent`;
- всё остальное — внутри.

Когда понадобится живой мастер — рядом с `AutoGameMaster` появится
`LiveGameMaster`, оба будут единообразно дёргать
`GameEngine.apply_master_intent`. Замена режима — флагом в сейве:
`master_mode: auto | live | hybrid`.

В `hybrid` сценарий идёт автоматически, но мастер может в любой момент
вмешаться. Это самый интересный режим: автомат двигает сюжет, живой
мастер «приукрашивает».

## 8. Что заложить сейчас (без UI мастера)

Чтобы потом не переписывать — уже в MVP:

1. **DTO разделение:** `PlayerCommand` ≠ `MasterIntent`. Даже если
   мастер-интенты сейчас никто не отправляет — типы есть, тесты есть.
2. **`apply_master_intent` метод на `GameEngine`** — есть, доступен
   тестам. Через него тесты прогоняют сложные сценарии.
3. **Поля сейва:** `master_pin_hash`, `master_mode`, `master_transparency`
   — есть в схеме, дефолтные значения «нет мастера».
4. **Событийная модель с тегами:** каждое событие может нести
   `tags: list[str]`, в том числе `"master_intervention"`.
5. **Чистое разделение «событие выпустилось» vs «событие применилось»**
   для бросков (см. `ENGINE.md` §6.2).

Этого хватит, чтобы потом добавить экран мастера, не трогая ядро.

## 9. Чего не делаем сейчас

- UI мастера — нет.
- PIN-вход — нет.
- Реализаций `MasterIntent` за пределами тестов — нет (но
  модуль `master_ops.py` с реализациями есть).
- Сетевого мастера — нет.
- LiveDiceRoller — нет (см. `ENGINE.md` §7).

Каждое из этого добавляется одним самостоятельным релизом, без
переделок ядра.
