# VISIBILITY — линия видимости, освещение, туман войны

Видимость в D&D — фундаментальная подсистема: от неё зависит «кого
можно атаковать», «откуда срабатывает Скрытая атака плута», «работает
ли тёмное зрение эльфа», «что игрок видит на карте». Архитектор явно
попросил заложить это в движок с самого начала.

Этот документ — спецификация. Реализация — в фазе после `Creature` и
`Battlefield`, но интерфейсы готовы уже сейчас.

---

## 1. Понятия

### 1.1 Освещение клетки (`LightLevel`)

```python
class LightLevel(StrEnum):
    BRIGHT = "bright"   # дневной свет / факел в радиусе
    DIM = "dim"         # сумерки / на краю радиуса факела
    DARK = "dark"       # полная темнота / подземелье без огней
```

Хранится в `Battlefield.lighting: dict[Square, LightLevel]`. Меняется
от:
* источников света (факел, фонарь, заклинание Light, костёр) —
  динамически;
* статичной разметки в YAML карты (по умолчанию всё `DARK` в
  подземелье, `BRIGHT` на улице днём).

### 1.2 Зрение существа (`Vision`)

```python
class Vision(StrEnum):
    NORMAL = "normal"           # видит BRIGHT нормально, DIM с помехой, DARK не видит
    DARKVISION_60 = "dv60"      # видит DARK как DIM в радиусе 60 фт
    DARKVISION_120 = "dv120"    # 120 фт (у больших драконов и т.п.)
    BLINDSIGHT_10 = "bs10"      # видит без зрения в радиусе 10 фт (нюх, эхо)
    TRUESIGHT = "truesight"     # видит сквозь иллюзии и невидимость в радиусе
```

`Creature.vision: tuple[Vision, ...]` — может быть несколько (эльф —
`(NORMAL, DARKVISION_60)`).

В MVP: люди — `NORMAL`, эльфы и большинство монстров — `DARKVISION_60`.

### 1.3 Препятствия

`Battlefield.terrain: dict[Square, Terrain]` определяет
**физическое** наличие препятствий. В контексте видимости важны:

* `Wall` — блокирует и движение, и LoS;
* `LowCover` — не блокирует LoS, но даёт +2 к КД (half cover);
* `HighCover` — блокирует LoS наполовину (three-quarters: +5 к КД);
* `Door(closed)` — блокирует LoS как стена; `Door(open)` — нет.
* `Smoke` / `Fog` — блокирует LoS полностью, но не движение
  (`heavy_obscured`).

### 1.4 Степени обзора (`ObscurementLevel`)

Производное от освещения и препятствий между точками:

```python
class ObscurementLevel(StrEnum):
    CLEAR = "clear"               # видно нормально
    LIGHTLY = "lightly"           # помеха на Perception-проверки
    HEAVILY = "heavily"           # эффективно слепые: помеха на атаки;
                                  # атаки против — с преимуществом
```

Книга 2024 (§«Зрение и свет»): в DARK с обычным зрением — `HEAVILY`;
в DIM с обычным или DARK с темнозрением — `LIGHTLY`; в BRIGHT —
`CLEAR`.

## 2. Сервис `VisibilitySystem`

Живёт в `application/engine/visibility.py`. Чистый, без I/O, получает
`Battlefield` и `state.creatures` в каждом вызове.

```python
class VisibilitySystem:
    def __init__(self, battlefield: Battlefield) -> None: ...

    def line_of_sight(self, frm: Square, to: Square) -> LosResult: ...
    """Есть ли LoS между клетками: учитывает стены, двери, дым/туман.
    Алгоритм — Брезенхэма по клеткам; если *любая* промежуточная
    клетка блокирует — нет LoS."""

    def obscurement_for(
        self, viewer: Creature, target: Square | Creature
    ) -> ObscurementLevel:
        """С учётом vision viewer и lighting клеток между."""

    def can_see(
        self, viewer: Creature, target: Square | Creature
    ) -> bool:
        """LoS + obscurement != HEAVILY + цель не Invisible (или viewer
        имеет TrueSight)."""

    def visible_squares(self, viewer: Creature, *, max_range: int = 60) -> set[Square]:
        """Все клетки в радиусе, до которых LoS и видимость > 0.
        Используется для тумана войны."""

    def party_fov(self, party: Party) -> set[Square]:
        """Объединение visible_squares всех живых PC партии. Это и есть
        партийный «туман войны» для MVP."""

    def cover_against(
        self, attacker: Creature, target: Creature
    ) -> Cover:
        """NONE / HALF / THREE_QUARTERS / TOTAL — для бонуса КД цели."""
```

`LosResult` несёт не только bool, но и причины: список клеток,
блокировавших, тип блокировки. Это нужно для UI («стрелка попала в стену»)
и для тестов.

---

## 3. Где это влияет на движок

* **Атака:** если `cover_against(...) == TOTAL` — атака невозможна
  (target нельзя выбрать). HALF — +2 к КД; THREE_QUARTERS — +5.
* **Атака с обскуренной цели:** если obscurement `HEAVILY` (например,
  атакующий не видит цель в темноте) — помеха.
* **Атака **по** обскуренному атакующему:** если viewer не видит
  атакующего — атаки против атакующего с **преимуществом** (книжное
  правило «невидимый атакующий»). Это симметричный эффект.
* **Скрытая атака плута:** требует выполнения одного из условий, одно
  из них — «вы видите цель и хотя бы один союзник плута в пределах
  5 футов от цели, не недееспособный, видит цель тоже». Visibility
  даёт нам ответы.
* **Невидимость:** существо `Invisible` — `obscurement HEAVILY` для
  всех (кроме TrueSight). См. `Condition: invisible`.
* **Заклинания с дальностью:** проверяют `distance + LoS`.
* **Реакции:** провоцированная атака требует, чтобы атакующий **видел**
  выходящего из досягаемости.

## 4. Туман войны в UI

### 4.1 MVP — общий партийный туман

`party_fov()` каждые `OnTurnEnd` пересчитывается. На карте боя:

* **Видимые сейчас** клетки — рендерятся как обычно.
* **Когда-то видимые** клетки (запомненные) — рендерятся **dim**,
  без существ (мы помним террейн, но не помним, где были враги).
* **Никогда не видимые** клетки — не рендерятся вовсе (тёмный фон).

Память партии — поле `GameState.explored: set[Square]` per-encounter.

### 4.2 Pост-MVP — per-character FoV

`Character.fov: set[Square]` для каждого PC. В hot-seat игрок видит
только то, что видит его PC. Партийный туман остаётся как
вспомогательный. Архитектура к этому готова — `VisibilitySystem`
уже работает на уровне `(viewer, target)`, агрегация партии — это
просто union.

## 5. Освещение от источников света

```python
class LightSource(BaseModel):
    owner: CreatureId | None       # факел у существа, или None для статичного
    position: Square | None        # для статичного; иначе из owner
    bright_radius: int             # фт
    dim_radius: int                # фт (внешний радиус, до которого свет DIM)
    duration_remaining: int | None # раунды; None = бесконечный
```

Источники хранятся в `Battlefield.light_sources: list[LightSource]`.
При движении владельца — позиция обновляется. При завершении
длительности — снимается. Заклинание `Light` (1-уровневое) — обычный
LightSource с `bright_radius=20, dim_radius=20, duration=600` (1 час).

При расчёте `Battlefield.effective_lighting(square)`:

1. Базовое освещение клетки (из карты).
2. Берём максимум по всем источникам (BRIGHT > DIM > DARK).
3. Препятствия (стены) — свет не проходит сквозь них; алгоритм тот же,
   что для LoS.

Это пересчитывается лениво при изменении источников или раз за раунд.

## 6. Скрытность (Stealth) и обнаружение

Связаны с видимостью, но это **другая** механика — действие Засада
(Hide), проверка `DEX (Stealth)` против пассивной `WIS (Perception)`
наблюдателей. Здесь не описываю подробно (см. `DESIGN.md` §4.1 раздел
«Засада»), но Visibility-сервис **участвует**: невидимое из-за
скрытности существо рендерится как `Invisible`-condition, и
applicable правила применяются.

## 7. Алгоритмы

### 7.1 LoS

Алгоритм Брезенхэма для линий на сетке. Промежуточные клетки —
проверяются по очереди; первая блокирующая прерывает.

**Симметрия и канонизация endpoint'ов.** Стандартный Брезенхэм
направленно-зависим: при `start→end` и `end→start` он может выбирать
разные клетки на диагоналях, что нарушает книжное правило «A видит B
⇔ B видит A». Перед запуском алгоритма пара endpoint'ов сортируется
лексикографически по `(x, y)` (`_canonical_segment`) — это даёт
детерминированную, симметричную трассу без потери информации. То же
применяется к `cover_against`. Property-тесты проверяют симметрию на
картах со случайными стенами.

**Endpoint'ы.** Клетки `frm` и `to` сами не блокируют LoS — book-правило
«вы видите то, на что навели». Для cover endpoint'ы исключаются из
обхода, но **`target` на TOTAL-cover клетке** (стена, закрытая дверь)
возвращает `TOTAL` отдельной веткой — «цель за полной защитой нельзя
выбрать целью» (книга стр. 25).

**MVP-упрощение «угла стены».** Полное wargame-правило «блокировка по
диагонали, если **обе** ортогональные смежные клетки — блокирующие» —
**не реализовано**. Стандартный Брезенхэм даёт «диагональ проходит»;
это согласовано с упрощённым DM-руководством. Зафиксировано тестом
`test_los_corner_of_wall_is_not_blocked_simplified` — реализация
полного правила обоснованно сломает этот тест.

### 7.2 Visible squares (FoV)

Симметричный shadow-casting: для каждого октанта вокруг наблюдателя
пускаем лучи (на самом деле — recursive shadow casting по сетке).

Альтернатива — наивный «LoS до каждой клетки в радиусе»: O(R²·R) на
радиус, для R=60ft=12 клеток это 12³ ≈ 1700 операций. На MVP — ОК.
Если станет узким местом — переделаем на shadow casting.

### 7.3 Cover

`cover_against(attacker, target)`:

1. Берём LoS-линию.
2. Проверяем, есть ли на пути:
   * существо (медиум-кляйнер, +2 к КД от союзников/нейтральных,
     0 — от врагов цели);
   * объект с `cover: HALF` (+2 к КД);
   * объект с `cover: THREE_QUARTERS` (+5).
3. Если несколько источников — берём **наибольший** (книга, §«Укрытие»).

## 8. Производительность

Все три операции — `los`, `obscurement_for`, `visible_squares` — кешируются
**внутри одного хода**. Кеш сбрасывается на любом из событий:
`CreatureMoved`, `TerrainChanged`, `LightSourceAdded/Removed`,
`ConcentrationDropped` (для иллюзий).

Это даёт ровно одну O(R³) операцию на ход существа, даже если 20
тестов «видит ли A B?».

## 9. Тесты

* Юнит на LoS: стена блокирует, открытая дверь — нет, закрытая — да,
  дым — да.
* Юнит на obscurement по комбинациям vision × lighting (таблица 3×3).
* Юнит на cover (none/half/three_quarters/total).
* Property-based: visible_squares ⊆ disk(viewer, radius).
* Property-based: симметрия LoS (`los(A, B) == los(B, A)` при
  отсутствии тонкого правила «угла»).
* Интеграционный: бой 1 из сценария-демо — обскуренная цель в углу
  туннеля → атака с помехой → проверка `AttackRolled` события с
  `disadvantage=True`.

---

## 10. Что отложено

* **3D освещение** (высоты, лестницы) — не делаем.
* **Цветной свет** (магический фиолетовый свет) — не нужно.
* **Звук как сенсор** (для blindsight тоньшего) — упрощено.
* **Per-character память карты** — пост-MVP, но интерфейс готов.
* **Светящиеся пятна заклинаний с разным радиусом** — да, поддержано
  через LightSource; разные тонкости (например, мерцающий факел) — нет.
