# DESIGN — бизнес-логика D&D-консоли

Документ фиксирует, **что** делает игра, в терминах правил D&D 5e (издание 2024).
Архитектура и пакеты описаны отдельно в [ARCHITECTURE.md](ARCHITECTURE.md).

Цель документа — служить контрактом между правилами книги и кодом: каждая глава
ниже отвечает на вопрос «как реализовать этот кусок правил так, чтобы он был
расширяемым и тестируемым».

---

## 1. Базовые понятия и принципы

### 1.1 Сущности первого порядка

| Сущность | Что моделирует |
|---|---|
| **Creature** | любое существо в игре (PC и NPC/монстр). Содержит характеристики, хиты, КД, состояния, владения, скорость, инвентарь. |
| **Character** | расширение `Creature` для персонажа игрока: уровень, опыт, мировоззрение, биография, ячейки заклинаний, прогрессия. |
| **Party** | партия игрока: `list[Character]` + связанные с ней флаги/настройки (например, `master_pin_hash`, `master_mode`). Living-state, попадает в сейв. См. `ENGINE.md` §1.2. |
| **Species** (вид/раса) | данные о виде: размер, скорость, особенности, тёмное зрение и т.п. |
| **CharacterClass** | класс: кость хитов, основные характеристики, владения, прогрессия особенностей по уровням, ячейки заклинаний. |
| **Background** | предыстория: 2 навыка + 1 инструмент, черта, начальное снаряжение. |
| **Item** | предмет: оружие, доспех, расходник, инструмент, прочее. |
| **Spell** | заклинание: уровень, школа, время накладывания, дистанция, концентрация/ритуал, компоненты, эффект. |
| **Encounter** | боевая сцена: список участников, инициатива, `Battlefield` с квадратной сеткой, состояние раундов. |
| **Battlefield** | поле боя: ширина/высота в клетках, террейн, освещение, занятость (`dict[Square, list[CreatureId]]`). См. `ENGINE.md` §2. |
| **Location** | узел графа мира: описание, выходы, NPC, скрытые объекты, события. |
| **Scenario** | сценарий мастера: набор локаций, NPC, событий, целей. Канонический термин — `scenario` / «сценарий» (не «приключение», не «кампания»). |
| **GameState** | состояние сохранения: партия, мир (флаги, текущая локация), активный сценарий, журнал событий. Сериализуется в сейв целиком. |
| **Sprite** | **контентный** объект (не доменный!) с ASCII-формами разных zoom-уровней для отображения существ и объектов. Живёт в `content/sprites/*.yaml`, не в `domain/entities/`. См. `UI.md` §4. |
| **LocStr** | bilingual-обёртка `{ en, ru }` для всех локализуемых полей контента (имена монстров, описания заклинаний и т.д.). См. `I18N.md` §4. |
| **CreatureSize** | enum размера существа: TINY/SMALL/MEDIUM/LARGE/HUGE/GARGANTUAN. В MVP все существа MEDIUM (1×1 клетка). См. `OPEN_QUESTIONS.md` Q35. |
| **DeathSaveState** | состояние спасбросков от смерти PC при 0 HP (0..3 успехов / провалов, stable). Поле на Character с самого начала. См. §2.5. |
| **TurnBudget** | бюджет ресурсов хода: action / bonus_action / reaction / movement / free_interaction. См. §4.2 и `OPEN_QUESTIONS.md` Q31. |
| **Target** | discriminated union целей действия: CreatureTarget / SquareTarget / AreaTarget / SelfTarget / AllInRangeTarget / MultiTarget. См. `TARGETING.md`. |
| **VisibilitySystem** | application-сервис, отвечающий на вопросы «видит ли A B?», «что видит партия?», «какое укрытие у цели?». См. `VISIBILITY.md`. |
| **MonsterAI** | стратегия выбора интента NPC. Профили: brawler/skirmisher/ranged/caster/support/coward + composite. См. `AI.md`. |
| **TurnIntent** | DTO, описывающий, что существо хочет сделать в свой ход (movement + action + bonus_action). Возвращается TurnIntentProvider'ом. |

**Канонические термины** для документации и кода — в [`GLOSSARY.md`](GLOSSARY.md).
**Состояния** (Conditions) — отдельный реестр; кастомные («кровотечение»,
«заморозка») реализуются как плагины Condition по той же схеме, что и
встроенные, и **не входят** в MVP-список (см. §5).

### 1.2 Принцип «всё через кости»

Любая неопределённость в правилах разрешается **броском с модификаторами**, а
не магическими числами в коде. Унифицированный движок костей (см. §3) — единая
точка входа для:

1. **Тест к20** (характеристика/навык/инструмент): `d20 + mod + proficiency?`.
2. **Спасбросок**: то же, но порог — Сложность (Сл.) задаётся источником угрозы.
3. **Бросок атаки**: `d20 + mod + proficiency` против КД цели, нат. 20 = крит,
   нат. 1 = промах.
4. **Бросок урона**: `NkX + mod` (для крита кости удваиваются, модификатор — нет).
5. **Бросок инициативы**: `d20 + DEX_mod`.

Преимущество/помеха — модификатор броска (бросаем два к20, берём больший/меньший);
они не складываются. Преимущество и помеха одновременно → обычный бросок.

### 1.3 Принципы разработки

- **Правила — данные, не код.** Список рас, классов, заклинаний, предметов,
  монстров — в YAML/JSON, загружаемых в SQLite (см. §10). Добавление новой расы
  не должно требовать изменения кода ядра.
- **Контентные источники подключаемы.** Папка `content/core` — базовая,
  `content/homebrew/*` — пользовательские паки, загружаются и накатываются поверх.
- **Случайность изолирована.** Все броски идут через объект `RNG`, его можно
  заменить детерминированным сидом для тестов.
- **События — через шину.** Бой, исследование, сценарии шлют события
  (`AttackHit`, `CreatureDied`, `EnterLocation`, `SkillCheckPassed`); сценарии
  слушают их и реагируют. Это даёт мастеру декларативную модель скриптов.

## 2. Характеристики, владения, КД

### 2.1 Шесть характеристик

`STR, DEX, CON, INT, WIS, CHA`, значение 1..30 (для существ; для PC обычно 1..20).
Модификатор: `floor((value − 10) / 2)`. Таблица в книге, формула равнозначна.

### 2.2 Бонус мастерства (БМ)

Определяется уровнем персонажа (или показателем опасности у монстра):

| Уровень | БМ | Уровень | БМ |
|---|---|---|---|
| 1–4 | +2 | 13–16 | +5 |
| 5–8 | +3 | 17–20 | +6 |
| 9–12 | +4 | | |

Бонус не складывается сам с собой (например, владение и тем же навыком одновременно).
Может быть удвоен (компетентность) или поделён вдвое — но и в этом случае применяется
один раз.

### 2.3 Владения

Существо может иметь владение:
- **навыком** (16 навыков: Атлетика, Акробатика, …) → БМ к тесту соответствующей
  характеристики;
- **инструментом** → БМ к тесту с этим инструментом, плюс преимущество, если
  ещё и навык применим;
- **спасброском** (даётся классом);
- **оружием/доспехом** → БМ к атаке этим оружием; без владения доспехом — помеха
  на STR/DEX тесты и атаки, нельзя творить заклинания.

### 2.4 Класс доспеха (КД)

Базовая формула: `КД = 10 + мод. Ловкости`.
Доспехи переопределяют её (например, `КД = 14 + мод. Ловкости (макс +2)`).
Щит даёт `+2`. Только **один** базовый расчёт КД одновременно (например, у
монаха Защита без доспехов и у чародея Драконья устойчивость — выбрать один).

### 2.5 Хиты, кость хитов, временные хиты, спасброски от смерти

#### Хиты и кость хитов
- **На 1 уровне** — `max(d_hit) + CON_mod`.
- **На каждом следующем** — `roll(d_hit) + CON_mod` (или среднее, округлённое вверх).
- **Кость хитов** — расходный ресурс на коротком отдыхе для лечения.
- **Временные хиты** не складываются между собой; не лечат и не превышают максимум.

#### Падение до 0 HP

**NPC (Monster)** — мгновенно мёртв (мастер может это переопределить
ad-hoc, см. `MASTER.md`).

**PC (Character)** — попадает в `DeathSaveState` (поле на Character):
- На начале каждого **своего** хода с 0 HP — спасбросок от смерти
  (бросок d20, без модификаторов).
- `>= 10` — успех (`successes += 1`), `< 10` — провал (`failures += 1`).
- **Нат-20** — восстановление 1 HP (выход из DeathSaveState).
- **Нат-1** — два провала.
- **Получение урона при 0 HP** — провал; если урон — крит, **два** провала.
- **Урон, превышающий максимум HP за один удар** — мгновенная смерть
  (правило «massive damage»).
- **3 успеха** — стабилизирован (`stable=True`), спасброски прекращаются;
  через 1 час восстанавливается 1 HP. На стабилизированного действуют
  обычные правила: лечение → выход из 0 HP.
- **3 провала** — смерть.
- **Стабилизация Медициной** (другое существо, действие, проверка
  WIS-Medicine DC 10) — `stable=True`.
- **Любое лечение** (>0 HP) — сбрасывает `DeathSaveState` (обнуляет
  successes и failures), существо приходит в сознание.

`DeathSaveState`:
```python
class DeathSaveState(BaseModel):
    successes: int = 0       # 0..3
    failures: int = 0        # 0..3
    stable: bool = False
```

Поле `Character.death_saves: DeathSaveState` всегда присутствует;
обновляется на каждом событии (получение урона, начало хода с 0 HP,
лечение). См. `OPEN_QUESTIONS.md` Q26.

#### Концентрация на заклинаниях

Существо может одновременно удерживать **только одно** заклинание,
требующее концентрации. Если кастуется второе concentration-заклинание
— первое автоматически сбрасывается.

**Прерывание концентрации** (Книга 2024 стр. 352, глоссарий «Концентрация»):

* При получении **ненулевого** урона существо делает спасбросок
  Телосложения с `DC = min(30, max(10, damage // 2))`. Верхняя граница
  30 фиксирована книгой. Провал — концентрация теряется.
* При **падении до 0 HP** (либо смерть) концентрация заканчивается
  **автоматически, без спасброска**.
* При получении состояния `Incapacitated` (включая `Stunned`,
  `Paralyzed`, `Unconscious`) — концентрация заканчивается.

Это работает как для PC, так и для NPC (поэтому реализуется на Creature,
не только на Character).

`Creature.concentration: SpellId | None` — поле, в MVP-классах
(Воин/Плут) всегда `None`. См. `OPEN_QUESTIONS.md` Q27.

### 2.6 Пассивная Внимательность

`10 + мод. Мудрости + (БМ, если владение Внимательностью)`. Используется
для скрытых ловушек, наблюдательности и т.п. Также — для пассивной
проверки видимости в обскурении и для обнаружения скрывающихся существ.

## 3. Кости

DSL для бросков (см. domain/dice.py):

```
d20                            # один к20
2d6+3                          # сумма двух к6 + 3
4d6kh3                         # 4к6, оставить три старших (генерация stats)
d20 advantage / disadvantage   # 2к20, max/min
3d8+5 crit                     # бросить дважды кости урона, +5 один раз
```

Парсер выражений + объект `RollResult { total, rolls, modifier, dice, kept }`.
Подменяемый `RNG` (real/seeded/fixed-sequence) — точка тестирования.

Бросок с преимуществом/помехой — флаг, а не отдельный синтаксис вызова.
«Героическое вдохновение» — реализуется как право один раз перебросить любой
бросок: возвращаемый результат поддерживает `.reroll()`.

## 4. Действия в раунд боя

Унифицированные **действия**, **бонусные действия**, **реакции** —
точки расширения для классов, заклинаний и предметов.

### 4.1 Базовый набор действий

| Действие | Эффект |
|---|---|
| Атака | один (или несколько, по особенности класса) бросок атаки. |
| Рывок | до конца хода +скорость к перемещению. |
| Отход | перемещение не вызывает провоцированных атак. |
| Уклонение | до начала след. хода атаки по вам — с помехой, спасброски Ловкости с преимуществом. |
| Помощь | следующий тест/атака союзника — с преимуществом. |
| Засада | проверка Скрытности. |
| Влияние | проверка взаимодействия с NPC (Обман/Запугивание/Выступление/Убеждение/Уход за животными). |
| Магия | накладывание заклинания/магического предмета. |
| Подготовка | действие в ответ на триггер (реакция отложенная). |
| Поиск | проверка Мудрости/Интеллекта/Восприятия. |
| Изучение | проверка Интеллекта (Аркана/История/Анализ/Природа/Религия). |
| Использование | использование немагического предмета. |

### 4.2 Action economy (бюджет хода)

Каждый ход существа в бою — это **бюджет ресурсов**, моделируемый
объектом `TurnBudget` (см. `OPEN_QUESTIONS.md` Q31):

| Ресурс | Сколько | Когда восстанавливается |
|---|---|---|
| **Action** | 1 | начало своего хода |
| **Bonus Action** | 1 | начало своего хода |
| **Reaction** | 1 | начало своего хода (сохраняется между ходами других) |
| **Movement** | =speed (фут) | начало своего хода; можно split до/после действия |
| **Free interaction** | 1 | начало своего хода (открыть дверь, обнажить меч) |

Бюджет создаётся свежий в `Encounter.run_turn()`, любое действие
проверяет наличие соответствующего ресурса через
`TurnBudget.consume_action()` и т.п.

#### Бонусные действия и реакции

- **Бонусное действие** — только при наличии прямого разрешения (умение,
  заклинание, особенность). Одно за ход.
- **Реакция** — одна между ходами. Самая частая — **провоцированная атака**
  (одна рукопашная атака врагу, который покидает досягаемость без Отхода/телепортации).

Реакции — отдельная категория `Action.category: REACTION` в едином
`ActionRegistry` (см. `OPEN_QUESTIONS.md` Q33 и аудит I-020). Триггер
вызывается через `EventBus`; для PC — `UserInterface.request_confirm()`,
для NPC — `MonsterAI.should_react()`. См. `AI.md` §6.

#### Multiattack

Некоторые классы и многие NPC получают возможность сделать **несколько**
бросков атаки за одно действие Атака:

- **Воин, уровень 5**: Extra Attack — 2 атаки.
- **Гнолл**: Multiattack 2.
- **Хобгоблин-капитан**: Multiattack 2 + бонус-удар щитом.

Моделируется полем `AttackAction.repeats: int` (по умолчанию 1, см.
`OPEN_QUESTIONS.md` Q32). Каждая атака — отдельный `AttackRoll` с
независимым выбором цели; UI спрашивает «куда направить вторую атаку»
после первой. Multiattack **не** распространяется на бонусные действия
(они отдельные).

### 4.3 Перемещение

- Скорость существа в футах (на 5 футов = 1 клетка). Движение допускается до и
  после действия (можно разбивать).
- Труднопроходимая местность — `×2` стоимость каждого фута.
- Провоцированная атака — при выходе из досягаемости (5 фут по умолчанию).

### 4.4 Атака и урон

Шаги:

1. **Выбрать цель** в пределах досягаемости/дистанции.
2. **Модификаторы**: преимущество/помеха (укрытие, невидимость, состояние,
   засада, бой под водой и т.п.), бонус мастерства, мод. характеристики.
3. **Бросок к20**. Сравнить с КД цели. Нат.20 — крит. Нат.1 — промах.
4. **Бросок урона**: кости оружия/заклинания + мод. атакующей характеристики.
   Крит — кости удваиваются (модификатор один раз). Сопротивление = ÷2,
   уязвимость = ×2; иммунитет = 0. Порядок: бонусы/штрафы → сопротивление →
   уязвимость (см. книгу).
5. **Применение последствий**: вычесть из временных хитов, потом из обычных;
   проверить переход в 0 хитов и т.д.

### 4.5 Укрытие

- Половина: +2 к КД и спасброскам Ловкости.
- Три четверти: +5.
- Полное: цель не выбирается.

### 4.6 Дальнобойные атаки

Имеют две дистанции: норм. и макс. За пределами норм. — помеха; за пределами
макс. — невозможно. Дальнобойная атака в рукопашной (рядом враг, видящий и
не недееспособный) — помеха.

### 4.7 Концентрация на заклинаниях

Если на заклинателе действует концентрация и он получает урон, он совершает
спасбросок Телосложения со Сл. = `max(10, урон / 2)`. Провал — концентрация
сорвана.

## 5. Состояния

Перечисляются как `Condition` (enum/класс):

`Bleeding (опц.), Blinded, Charmed, Deafened, Exhaustion (с уровнями),
Frightened, Grappled, Incapacitated, Invisible, Paralyzed, Petrified,
Poisoned, Prone, Restrained, Stunned, Unconscious`.

Каждое состояние — объект с:

- идентификатором;
- эффектом (модификатор бросков, ограничения действий, КД-модификаторы и т.п.);
- длительностью (раунды, до спасброска, до условия);
- кто наложил (для развеять).

Состояния не складываются (одно действующее наибольшее по эффекту).
Состояние снимается чёткой триггерной механикой: `try_end_at_turn_start/end`,
`end_on_save(stat, dc)`, `end_on_damage`, `end_on_action(name)`.

В коде состояния — **плагины**: реализуют интерфейс `Condition`, регистрируются
в `ConditionRegistry`, цепляются к существу через `CreatureStatusTracker`.
Это даёт расширяемость (например, добавить «Кровотечение» как пользовательское
состояние — без правок ядра).

### 5.1 Истощение — отдельная подсистема (не Condition)

Истощение (Exhaustion) — **единственное** накапливаемое состояние книги,
устроено принципиально иначе. По решению Q34 моделируется отдельно:

- `Creature.exhaustion: int` — поле, 0..6.
- Применяется через `Creature.add_exhaustion(n=1)` / `Creature.remove_exhaustion(n=1)`.
- На уровне 1–5: каждый уровень даёт **-2 ко всем тестам к20**
  (характеристик, спасбросков, атак). Это применяется автоматически
  через `Modifier`-источник `source_kind=exhaustion`, добавляемый при
  изменении уровня.
- На уровне **6** — существо мгновенно мертво.

Источники истощения: магия, отсутствие отдыха более 24 часов, конкретные
эффекты заклинаний. Снятие — продолжительный отдых (минус 1 уровень за
отдых) или конкретные заклинания/предметы.

### 5.2 Базовые состояния MVP

| Condition | Что делает (кратко) |
|---|---|
| **Blinded** | помеха на атаки; атаки против — с преимуществом; провал любого теста, требующего зрения. |
| **Charmed** | не может атаковать чарователя; чарователь — с преимуществом на социальные тесты. |
| **Frightened** | помеха на тесты и атаки, пока источник страха в поле зрения; не может приближаться. |
| **Grappled** | скорость = 0; снимается при отходе захватчика или Acrobatics/Athletics-проверке. |
| **Incapacitated** | без действий, бонусных действий, реакций. |
| **Invisible** | атаки против — с помехой; атаки от — с преимуществом; видимость — особая (см. VISIBILITY.md). |
| **Paralyzed** | Incapacitated + не может двигаться/говорить; провал STR/DEX-спасбросков; атаки в 5 фт — крит. |
| **Petrified** | как Paralyzed, плюс ×10 вес, сопротивление всему урону. |
| **Poisoned** | помеха на атаки и тесты к20. |
| **Prone** | атаки на расстоянии — с помехой; атаки в 5 фт по нему — с преимуществом; вставание стоит ½ скорости. |
| **Restrained** | скорость = 0; атаки против — с преимуществом; атаки от — с помехой; помеха на DEX-спасбросках. |
| **Stunned** | Incapacitated; не может двигаться; провал STR/DEX-спасбросков; атаки против — с преимуществом. |
| **Unconscious** | Incapacitated; лежит на полу; не может двигаться/говорить; не осознаёт окружения; провал STR/DEX-спасбросков; атаки в 5 фт — крит. |

В MVP реализуем **8** наиболее частых (помеченных жирным в `tasks` #28).
Остальные — добавляются как новые плагины без правок ядра.

## 6. Создание персонажа

Реализуем 5 шагов из книги (стр. 31–39) как **визард-цепочку**, где каждый шаг —
команда + чистая функция перехода между состояниями билдера.

### Шаг 1: Класс

Игрок выбирает один из `CharacterClass` (минимум 2 для MVP — **Воин и Плут**;
комбинация «удар в лоб» + «скрытность и обход» точно ложится в сценарий-демо,
см. `OPEN_QUESTIONS.md` Q3). Сохраняется: уровень=1, опыт=0, кость хитов,
владения доспехами/оружием/спасбросками.

### Шаг 2: Происхождение

Выбор `Species` (минимум 2 для MVP — Человек и Эльф) и `Background`. Учитываются:
- Размер и скорость от вида.
- Особенности вида (тёмное зрение, фейское наследие, …).
- Черта от предыстории + 2 навыка + 1 инструмент + начальное снаряжение.
- 2 языка (один — Общий).

### Шаг 3: Характеристики

Три способа генерации, реализуем все:

1. **Стандартный набор** `[15, 14, 13, 12, 10, 8]` — расставить по характеристикам.
2. **Случайно**: `4d6 keep-highest-3` ×6, в порядке выбора.
3. **Покупка за очки** (Point Buy): 27 очков, стоимости из таблицы.

После назначения — корректировка от **предыстории**: либо `+2 / +1`, либо
`+1 / +1 / +1`, не выше 20.

### Шаг 4: Мировоззрение

9 мировоззрений (`LG, NG, CG, LN, N, CN, LE, NE, CE`).

### Шаг 5: Подробности

Рассчитываются автоматически:

- модификаторы характеристик;
- КД из доспеха/щита/Ловкости + классовые альтернативы;
- инициатива = `DEX_mod`;
- пассивная Внимательность = `10 + WIS_mod + БМ(если владение)`;
- хиты максимум = `max_d_hit + CON_mod`;
- ячейки заклинаний от класса/уровня;
- бонус атаки заклинанием/Сл. спасброска;
- бонусы спасбросков и навыков с учётом владений.

Реализация: класс `CharacterBuilder` с пошаговым API:

```python
builder = CharacterBuilder(content_repo)
builder.choose_class("воин")
builder.choose_species("человек")
builder.choose_background("солдат")
builder.assign_abilities(StandardArray(...))
builder.choose_alignment(Alignment.LG)
builder.finalize_details(name="Аэлар")
character = builder.build()
```

### Прогрессия и мультикласс

- `Character.gain_xp(amount)`; уровень рассчитывается по таблице 1..20.
- При повышении уровня: HP +`roll(d_hit) + CON_mod` (или среднее), новые особенности
  класса, БМ пересчитывается из общего уровня.
- **Мультикласс**: требование — 13 в основной характеристике обоих классов.
  Хиты — новый класс. БМ — по общему уровню. Владения — только подмножество
  от нового класса (см. книгу). Заклинания — комбинированная таблица.

Реализация прогрессии — стратегия `LevelUpStrategy` per class (содержит таблицу
«уровень → список features»). Особенности класса — также подключаемые объекты
(см. §11 о расширяемости).

## 7. Боевой движок

### 7.1 Жизненный цикл боя

```
EncounterBuilder → Encounter.start()
  ├─ roll_initiative_for_each()
  ├─ resolve_surprise()
  ├─ while not finished:
  │    for participant in initiative_order:
  │       on_turn_start(participant)
  │       run_turn(participant)
  │       on_turn_end(participant)
  │    round += 1
  └─ on_encounter_end()
```

Где:

- `on_turn_start/end` — триггеры состояний (например, отравленный делает спасбросок,
  кровотечение наносит урон, преимущество от Уклонения сбрасывается).
- `run_turn` — даёт игроку (или ИИ для NPC) выбрать действие, перемещение,
  бонусное действие. Игровой ввод — через **порт** `TurnIntentProvider`
  (см. §11), что позволяет иметь и CLI, и автоматический ИИ-противника.

### 7.2 Завершение боя

- Все враги выведены из строя/мертвы/сдались/сбежали → **победа партии**.
- Все PC выведены из строя → **поражение** (TPK или плен — решает сценарий).
- Партия покинула карту (например, через побег) → **побег**.

Побег — особая механика: персонаж заявляет о намерении сбежать, делает действие
Отход и движение к границе сцены. ИИ врагов может его догнать. После выхода —
персонаж покидает encounter, остальные продолжают.

### 7.3 Награды за бой

`Encounter.rewards` рассчитываются заранее:

- **Опыт**: сумма XP убитых монстров (берём из статблоков). Делится между PC.
- **Сокровища**: монеты + предметы. Реализуем «trove» — `LootTable` с весами
  (выпадает случайный набор).

После боя — экран распределения добычи, экипировки (с проверкой владений).

### 7.4 Реакции и провоцированная атака

Реализация — событийная. Перемещение существа в досягаемости врага шлёт
`MovingOutOfReach`; все участники с свободной реакцией могут заявить
`OpportunityAttack` (для PC — спросить интерактивно, для NPC — стратегия).

### 7.5 Зависимость от мастера/сценария

Сценарий может **вмешиваться в бой**: через события (`OnEncounterRound`)
запускать подкрепления, диалог в середине боя, обвалы и т.д.

## 8. Исследование мира

### 8.1 Модель мира

Мир — **граф локаций**. Каждый `Location`:

- `id`, `title`, описание (текст + опционально ASCII-арт);
- `exits: {direction: location_id}` (или `condition_to_exit`);
- `props`: интерактивные объекты (двери, сундуки, рычаги, картины);
- `npcs`: список NPC;
- `events`: список триггеров (см. ниже);
- `tags`: метки для запросов сценарием (`{indoor, magical, dark, …}`).

Освещение, шум, скрытность и т.п. — атрибуты локации, влияющие на проверки.

### 8.2 Что игрок делает в исследовании

В отличие от боя — **нелинейно**, без раундов. Команды:

- движение (`go north`, `выйти в коридор`);
- осмотр (`look`, `осмотреть камин`);
- использование предмета;
- разговор с NPC (`talk to ...`);
- проверка навыка явная (`search`, `study painting`) — сценарий назначит Сл.;
- использование заклинания вне боя (если подходит);
- отдых: короткий/продолжительный (с учётом «безопасно ли место»).

### 8.3 Скрытые объекты и проверки

При входе в локацию мастер (сценарий) может вызвать **пассивные проверки**:

- Если у кого-то из партии пассивная Внимательность ≥ Сл., он замечает
  скрытое автоматически. Иначе — нужен явный `Search`.

Локация имеет `secrets` — список объектов с `discoverability` (DC, способ).

### 8.4 Социальное взаимодействие

Базовая модель отношений NPC: `friendly | neutral | hostile`. Меняется по
триггерам (диалогам, действиям). Влияние — действие, проверка `CHA(Обман/
Убеждение/Запугивание)` или `WIS(Уход за животными)`.

Диалоги — деревья реплик в YAML, узлы помечены условиями
(`requires: {skill: deception, dc: 15}` или `requires: {flag: hollow_oak.read_ritual_scroll}`).

### 8.5 Отдых

- **Короткий отдых (1 час)**: тратятся кости хитов на лечение, восстанавливаются
  некоторые способности.
- **Продолжительный отдых (8 часов)**: полные хиты, восстановлено половина костей
  хитов, восстановлены все ячейки заклинаний.

Сценарий может запретить отдых в локации (опасная зона, погоня, прерывание
случайной встречей).

## 9. Сценарии мастера

Самая важная для расширяемости часть. Сценарий — **декларативный объект**,
без хардкода в Python.

### 9.1 Структура сценария

YAML-файл (фрагмент демо-сценария «Hollow Oak Mine» / «Шахта Гнилого Дуба»;
полное описание — в [`SCENARIO_DEMO.md`](SCENARIO_DEMO.md)):

```yaml
id: hollow-oak-mine
title:
  en: "Hollow Oak Mine"
  ru: "Шахта Гнилого Дуба"
version: 1
xp_curve: fast
start_location: forest-entrance
flags_initial:
  found_relic: false
  read_ritual_scroll: false
locations:
  - id: forest-entrance
    title:
      en: "Forest Entrance"
      ru: "Вход в лес"
    description:
      en: "A trail through dense woods ends at gnarled roots..."
      ru: "Тропа через густой лес обрывается у узловатых корней..."
    exits:
      down: main-tunnel
    events:
      - on: enter
        say:
          en: "The creaking bridge sways under your weight..."
          ru: "Скрипящий мост раскачивается под вашим весом..."
  - id: main-tunnel
    title:
      en: "Main Tunnel"
      ru: "Главный туннель"
    description:
      en: "Dim torchlight reveals three goblins around a campfire."
      ru: "Тусклый свет факелов выхватывает трёх гоблинов у костра."
    exits:
      back: forest-entrance
      south: trap-junction
    events:
      - on: enter
        encounter: goblins-3
encounters:
  - id: goblins-3
    monsters:
      - { kind: goblin, count: 3 }
    rewards:
      xp_total: 75
      loot:
        - { item: thieves-tools, chance: 0.5 }
        - { coins: { sp: 8 } }
npcs:
  - id: village-elder
    name:
      en: "Village Elder"
      ru: "Староста"
    disposition: friendly
    dialogue: dialogues/village_elder.yaml
```

Все локализуемые поля — `LocStr` (см. `I18N.md` §4). Идентификаторы
(`id`, ссылки `item: …`, `encounter: …`) — латиницей, не локализуются.

### 9.2 Триггеры событий

Универсальная модель «**when–condition–effect**»:

- **when**: `enter | leave | turn_start | use_item:item_id | skill_check:passed/failed | combat_round:N | encounter_end | flag_changed:name`.
- **condition**: булева формула над флагами/состоянием партии.
- **effect**: одно или цепочка из:
  - `say` — описание;
  - `set_flag` — изменить флаг;
  - `start_encounter` — запустить бой;
  - `give_item`, `take_item`, `give_xp`, `give_gold`;
  - `move_party` — переместить партию в локацию;
  - `require_check` — потребовать проверку;
  - `unlock_exit`, `lock_exit`;
  - `spawn_npc`, `kill_npc`;
  - `branch` — выбор по условиям.

### 9.3 Динамика сценария

Сценарий запускается через **движок сценария** (см. ARCHITECTURE), который
слушает `EventBus` и сравнивает каждое событие с зарегистрированными триггерами.
Это даёт декларативное «вступление в бой начинается, когда партия впервые
открывает дверь в хранилище».

### 9.4 Случайные встречи

`EncounterTable` — таблица с вероятностями. На `LongRest`/`Travel` мастер
бросает к100 и при попадании запускает встречу из таблицы. Таблица — данные.

### 9.5 Журнал и цели

`Quest` имеет цели (`Objective`), флаги. Сценарий помечает их через эффекты
(`complete_objective: rescue-ireena`). Игрок видит журнал, цели обновляются
по событиям.

## 10. Инвентарь, экипировка, награды

### 10.1 Инвентарь

- Слоты экипировки: `armor, shield, main_hand, off_hand, ranged, neck, ring×2, cloak, head, boots, hands`.
- «Рюкзак» — список предметов с весом (опционально энфорсим грузоподъёмность).
- Предмет может быть «свойствами»: `two_handed, versatile(d8/d10), light, heavy,
  finesse, thrown(20/60), ammunition, reach, loading, special, magic`.

### 10.2 Экипировка и владения

Надеть доспех = `equip(armor)`. Если у персонажа нет владения категорией — на
него вешается **штраф без владения**: помеха на STR/DEX тесты и атаки,
неспособность творить заклинания, пока в доспехе.

Атака оружием прибавляет БМ только при владении этим оружием/категорией.

### 10.3 Награды за бой

`LootTable` — список записей `{ item_id | gold_range, weight }`. Бросок к100
по таблице. После боя — экран распределения, можно «забрать всё», «разделить
поровну», «отдать одному».

### 10.4 Опыт

`Character.gain_xp(xp)`: при пересечении порога — `level_up`. XP за бой —
из статблоков монстров.

## 11. Расширяемость (точки гибкости)

Где система должна позволять «добавить новое без правок ядра»:

| Точка расширения | Как реализуется |
|---|---|
| Раса/вид | YAML-файл + регистрация в `species` репозитории. Особенности — ссылки на `Feature` (плагин). |
| Класс | YAML с прогрессией: `level → features` и `level → spell_slots`. Особенности — плагины. |
| Особенности (Feature) | реализуют интерфейс `Feature`, регистрируются по имени в `FeatureRegistry`. |
| Состояние (Condition) | реализуют интерфейс `Condition`, `ConditionRegistry`. |
| Заклинание | YAML + опционально плагин-эффект. Простейшие — данными (урон, спасбросок), сложные — кодом-плагином. |
| Оружие/доспех/предмет | YAML с свойствами; «магические эффекты» — плагин-обработчик. |
| Монстр | YAML-статблок + опц. ИИ-стратегия (`MonsterAI`). |
| Сценарий | YAML (§9). |
| Действие | реализует `Action`, регистрируется в `ActionRegistry`. |
| Реакция | реализует `Reaction`, `ReactionRegistry`. |
| Интерфейс | реализует `UserInterface` (CLI/TUI/тестовый mock). |
| ИИ существа | реализует `MonsterAI` (`pick_intent(state) -> Intent`). |

Везде, где «реализуют интерфейс», — это abstract base class в `domain`,
конкретные реализации — в `infrastructure/content` или поставляются плагинами.

## 12. Сохранение состояния

`GameState` — корень: партия (список Character), мир (флаги, посещённые
локации, текущий узел), активный сценарий (id + версия), журнал.

Сохранение в SQLite — отдельная таблица `saves(id, name, created_at, blob)`.
`blob` — сериализованный (JSON) снэпшот; домен предоставляет
`save/load_snapshot()`, репозиторий — `SaveRepository`.

Версия сценария фиксируется при старте, чтобы не сломаться при обновлении
контента.

## 13. Минимально жизнеспособная игра (MVP)

Чтобы проект можно было «играть руками», MVP включает:

- 2 расы: **Человек, Эльф** (см. `OPEN_QUESTIONS.md` Q3).
- 2 класса: **Воин (Чемпион)** и **Плут (Вор)** — уровни 1–3
  (см. `OPEN_QUESTIONS.md` Q3, `PROGRESSION.md`). Заклинаний MVP-классы не
  имеют — это сознательное упрощение, чтобы не тащить в первый релиз всю
  систему ячеек и компонентов; полная реализация заклинаний добавляется
  пост-MVP с появлением Волшебника/Жреца.
- 3 предыстории: Солдат, Мудрец, Преступник.
- Базовое оружие: меч, кинжал, короткий меч, лук, ручной арбалет; доспех:
  кольчуга, кожаный, наборный; щит.
- Состояния: Отравлен, Испуган, Ошеломлён, Парализован, Бессознательный,
  Лежащий ничком, Невидимый.
- Базовые монстры: Скелет, Гоблин (включая гоблина-лучника и гоблина-шамана),
  Волк, Орк, Гиеноид (Gnoll).
- Магические/расходные предметы для MVP-классов: зелье лечения,
  Талисман Стойкости (бонус-предмет из сценария), рунический камень с
  одной зарядкой заклинания (для тех, у кого нет ячеек).
- Один сценарий-демо **«Шахта Гнилого Дуба»** (Hollow Oak Mine) из 6
  локаций, 3 боёв, 1 загадки, скрытой комнаты и альтернативного пути; см.
  `SCENARIO_DEMO.md`.
- CLI команды: создать персонажа, начать сценарий, играть, сохранить/
  загрузить, показать лист персонажа, выйти.
- Ретро-TUI: 80-колоночный (минимум) псевдо-CRT интерфейс, рамки, **2 темы**
  оформления — `color` (по умолчанию) и `monochrome` (см. `UI.md` §3,
  `OPEN_QUESTIONS.md` Q9). Дополнительные темы (phosphor/amber/vga-16)
  добавляются как CSS-варианты без правок кода, если архитектор пожелает.

Всё, что сверх MVP, реализуется через те же точки расширения без правок ядра.

## 14. Что считаем не-целью

Чтобы избежать раздувания скоупа:

- Полная книга игрока 2024 (все 12 классов, 48 подклассов, 11 видов) — нет.
- Мультиплеер по сети — нет (только локальный hot-seat в направлениях развития,
  см. `ROADMAP.md` §9). Сейв — один. Мастер — автоматический движок сценариев
  (`ScenarioRuntime` = `AutoGameMaster`); живой мастер — пост-MVP, см.
  `MASTER.md`.
- 3D/графика — нет (только текст и ASCII-арт).
- Большие существа (Large/Huge/Gargantuan), занимающие несколько клеток — нет,
  только Medium. См. `ENGINE.md` §10.

**Боевая сетка — квадратная**: 1 клетка = 5 футов, 8 соседей, Chebyshev-
дистанция. Это решение архитектора, см. [`ADR/0002-square-grid.md`](ADR/0002-square-grid.md)
и [`ENGINE.md`](ENGINE.md) §2. На одной клетке могут стоять несколько существ
(дружественные проходят свободно; через враждебного — нельзя).
