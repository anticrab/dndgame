# ROADMAP — направления развития и этапы

Документ задаёт **порядок** и **границы** этапов разработки. Каждый этап
определяется через входы (что должно быть готово), выходы (Definition of Done),
ключевые риски. Цель — никогда не делать «всё сразу»; продвигаемся вертикально:
каждый этап даёт **запускаемый** продукт.

Звёздочкой `*` помечены направления, заложенные сейчас «на будущее»: код пишем
так, чтобы они не требовали ломающих изменений, но реализацию откладываем.

## 1. Ядро правил (domain core) — *в работе*

Иммутабельные value-объекты и базовые механики, без I/O.

- ✅ Кости (`DiceExpr`, `RollResult`, преимущество/помеха/крит).
- ✅ Характеристики (`Ability`, `AbilityScore`, `AbilityScores`, модификаторы).
- ✅ RNG-порт + Real/Scripted.
- 🔜 Хиты, временные хиты, кость хитов.
- 🔜 Типы урона, сопротивление/уязвимость/иммунитет.
- 🔜 Навыки, бонус мастерства, владения (оружие/доспех/инструмент/спасброски).
- 🔜 Состояния: базовый класс `Condition` + регистр; «ленивый набор» (Лежащий,
  Отравлен, Испуган, Парализован, Бессознательный, Невидимый).
- 🔜 Сущности: `Creature` (общий), `Character` (с уровнем/опытом),
  `Monster` (со статблоком и `MonsterAI`-стратегией).
- 🔜 `Spell`, `Item` (оружие, доспех, расходник, инструмент, магический).

**DoD:** ≥80% покрытия по domain тестами, `Creature` умеет получать урон,
лечиться, валиться в 0 хитов, делать спасбросок от смерти, накладывать/снимать
состояния. Логика чистая, без I/O.

**Риск:** перерастание domain в кашу. Контрмера — отдельные подпакеты
(`values/`, `entities/`, `rules/`, `conditions/`, `actions/`, `features/`).

## 2. Игровой движок и пошаговый бой

Единый `GameEngine` — центральный объект, оркеструющий тики и подсистемы
(см. `docs/ENGINE.md`).

- 🔜 `Battlefield` с **квадратной сеткой** (`(x, y)` int, Chebyshev-дистанция,
  8 соседей; см. `ADR/0002-square-grid.md`), позиционирование,
  движение, дистанции, провоцированные атаки, укрытие, террейн.
- 🔜 `Encounter` поверх Battlefield: инициатива, раунд/ход, очередь.
- 🔜 Действия как Command-объекты: Атака, Уклонение, Рывок, Отход, Помощь,
  Засада, Поиск, Магия (плейсхолдер), Использование.
- 🔜 Реакции: провоцированная атака.
- 🔜 Применение урона и спасброски по событиям.
- 🔜 Награда (XP, лут) по завершении.
- 🔜 Побег: отдельный режим выхода с карты.

**DoD:** можно прогнать сценарий «персонаж против гоблина» в скрипте — без UI,
по событиям; e2e-тест воспроизводим благодаря `ScriptedRNG`.

**Риск:** хочется впихнуть в движок UI. Контрмера — движок шлёт `Event`-ы,
UI слушает.

## 3. Создание персонажа и прогрессия

- 🔜 `CharacterBuilder` (Builder): класс → происхождение (вид+предыстория) →
  характеристики (3 стратегии) → мировоззрение → детали.
- 🔜 Расчёт КД/инициативы/пассивной Внимательности/ячеек заклинаний.
- 🔜 Прогрессия по уровням (1 → 3 для MVP), кость хитов, особенности класса.
- 🔜 «Быстрая» XP-кривая (см. `docs/PROGRESSION.md`), включая level-up
  посреди боя.
- 🔜 Инвентарь и экипировка с проверкой владений.

**DoD:** в коде можно создать PC из YAML-данных за ≤5 строк скрипта и попасть
в `Encounter`; повышение уровня меняет хиты/особенности корректно.

## 4. Хранение и сейвы

- 🔜 SQLite-схема: справочники контента (расы/классы/предметы/монстры/
  заклинания/предыстории/таблицы), таблица `saves`, таблица `settings`.
- 🔜 Миграции — простой кат-ап SQL-скриптов в `migrations/`.
- 🔜 Репозитории (`*Repository`) по требованию `req.md`.
- 🔜 `SaveService.save/load` — сериализация состояния (JSON в BLOB).

**DoD:** `dnd db init && dnd db seed` создаёт БД, можно сохранить/загрузить
состояние партии и продолжить с того же тика.

**Риск:** ORM-зуд. Не используем ORM — у нас простой sqlite3 + явный SQL,
учебная цель видеть Repository.

## 9. Расширяемость к multi-actor *

Сейчас один игрок управляет одним PC. По решению архитектора **порты под
будущие режимы не вводим заранее**, но пишем код так, чтобы каждое из
направлений добавилось без ломающих изменений.

Направления развития (порядок ориентировочный):

- **9a. Hot-seat** (один экран, несколько PC, передача управления, приватная
  панель мастера через PIN). Заложен в `UI.md` §8–9 и `ENGINE.md` §8.
- **9b. Live-мастер** — рядом с `AutoGameMaster` (`ScenarioRuntime`)
  появляется `LiveGameMaster` с собственным экраном и чит-консолью. См.
  `MASTER.md`.
- **9c. Сетевой режим** — host-сервер + клиенты. См. ниже §10.

**Что заложено сейчас (без портов):**

- 🔜 Все интенты (`PlayerCommand`) и события (`EngineEvent`) — pydantic-DTO,
  сериализуемые в JSON.
- 🔜 Раздельные типы `PlayerCommand` и `MasterIntent`; `GameEngine` имеет
  метод `apply_master_intent` (сейчас вызывается только из тестов).
- 🔜 `EventBus` — единственный канал событий движка наружу.
- 🔜 `RNG` и будущий `DiceRoller` — за портами; ни одно правило не вызывает
  `random.*` напрямую.
- 🔜 UI и БД — за портами. Domain не знает про них.

Этих инвариантов хватит, чтобы потом подключить hot-seat, мастера и сеть
за дни, а не месяцы. Любое нарушение инварианта блокирует MVP-PR.

**DoD MVP:** один локальный игрок проходит сценарий-демо; в коде нигде
не нарушены инварианты выше.

## 10. Сетевой режим (далёкое будущее) *

Описание здесь — на уровне «как не закрыть себе дверь». Реализация —
отдельный мажорный релиз после `1.0`.

- Транспорт — WebSocket или JSON-RPC поверх TCP, добавляется как
  адаптер слоя `infrastructure`.
- Host = `GameEngine` + сервер сокетов.
- Client = тонкий UI, слушает события, шлёт команды.
- Авторизация: PIN-коды игроков и мастера, как в hot-seat.

Это уже **не закладка** в коде; добавление будет своей серией PR.

## 11. Локализация (i18n)

См. `I18N.md`. Сжатый план:

- 🔜 Babel + gettext, `.po`/`.mo`-файлы.
- 🔜 Базовый язык — `en`. Русский — переключаемая локаль.
- 🔜 Контент в YAML — inline-словарь `{ en: "...", ru: "..." }` для
  всех локализуемых полей (`LocStr`).
- 🔜 UI-строки — через `_()`-обёртку; никаких конкатенаций.
- 🔜 Команды `make i18n-extract` / `make i18n-update LANG=ru` /
  `make i18n-compile`.

**DoD MVP:** UI работает на обоих языках, переключение в настройках,
сценарий-демо имеет полный bilingual-текст.

## 13. Открытый мир (после MVP)

Когда сценарий-демо пройдёт стабильно — переходим к открытому миру:
- множественные сценарии-«мини-приключения», объединённые миром.
- глобальная карта (overland), путешествие между локациями.
- система квестов с возможностью отказаться/прервать.
- развитые диалоги с NPC, репутация фракций.
- генеративные случайные встречи.
- крафтинг, торговля.
- собственно — постепенный путь к **режиму «помощник за столом»**: когда
  приложение помогает живому мастеру и игрокам, а не ведёт их по рельсам.

Это не задачи MVP; они здесь, чтобы помнить вектор.

## Порядок прохода

```
1 ────────► 2 ─┬───► 3 ─┬───► 5 ─┬───► 6 ─┬───► 7 ─┬───► 8 ─┬───► 12

              └───► 4 ─┘        │        │        │        │

                                          9, 11 (вшито в дизайн каждого слоя)
                                          10, 13 — после MVP
```

Поясняю порядок:
- Слой 1 нужен для всего. Без него правил нет.
- Слой 2 (движок + бой на квадратах) — сердцевина; ему нужен только domain.
- Слой 3 (создание персонажа) — нужны domain и контент-формат, можно
  параллельно с 4.
- Слой 4 (БД / сейвы) — независимый, параллельно с 3.
- 5 → 6 → 7 → 8 — стандартная последовательность вверх по стеку.
- 9 (multi-actor инварианты) и 11 (i18n) — не «отдельные этапы», а
  **контракты**, которые мы кладём в каждый слой сразу.
- 12 — параллельная инвестиция в каждом этапе.
- 10 (сеть) и 13 (открытый мир) — пост-MVP.

## Следующие этапы (U–Y) — за пределами боёвки

> Боевой вертикальный срез готов (классы L1–3, заклинания, состояния — серии
> P/Q/R/T). Дальше — недостающее для полного цикла сессии: «создать героя →
> исследовать мир → встречи/бой → лут и прокачка». Приоритет — по зависимостям;
> каждый этап data-driven (реестры/YAML), domain не зависит от application,
> отдельный spec → plan → TDD.

- **U — Используемые предметы (приоритет 1, быстрая победа).** `UseItemAction` +
  `ItemEffectRegistry` (heal / cast-from-scroll / buff / свет), эффект задаётся
  данными в `items.yaml` (`effect: ...`). Зелье лечит, свиток кастует.
  Переиспользует `SpellEffectRegistry`/`ResourceRegistry`. Малый объём, видимый
  результат, без новых подсистем. «Оживляет» готовый инвентарь (этап O).
- **V — Навыки и проверки характеристик (приоритет 2, фундамент).** `Skill`
  (18 навыков, данные) + владения/Expertise на `Creature`; служба
  `ability_check` (`d20 + mod + prof`, advantage/disadvantage от состояний — через
  `ConditionService`), пассивная Внимательность. Закрывает R2-навыки и
  разблокирует Fast Hands/Second-Story Work (отложено в T4) и проверки в
  исследовании. См. `docs/SKILLS.md`.
  - ✅ **V1 — фундамент:** `Skill`/`SKILL_ABILITY`, `Creature.skill_proficiencies/
    skill_expertise`, `skill_bonus`/`ability_check_bonus`/`roll_ability_check[_raw]`/
    `passive_score`, владения данными класса/шаблона.
  - 🔜 **V2 — боевые проверки:** `opposed_check` (состязания), состояния
    Grappled/Hidden, действия Shove/Grapple/Hide.
- **W — Создание персонажа и экипировка (приоритет 3).** `CharacterBuilder`
  (класс → вид + предыстория → характеристики (стандартный массив/покупка
  очков) → экипировка → стартовые фичи); **интерактивный выбор боевого стиля /
  подкласса** (закрывает отложенное из T4, см. `project_interactive_choice_
  deferred`); TUI-экран + `dnd character new`. Виды/предыстории — данные
  (`species.yaml`/`backgrounds.yaml`). Использует навыки (V) и предметы (U).
- **X — Исследование мира (приоритет 4, крупнейший; на фундаменте U/V/W).**
  `ScenarioRuntime` поверх `EventBus`: локации и переходы, NPC, диалоги
  (дерево реплик), журнал квестов + флаги мира, skill-gated челленджи (проверки
  V), скрытые объекты, триггеры; отдельный режим исследования в TUI. Разбить:
  - **X0 — фундамент: `GameSession` + `GameClock` + длительности + цикл
    исследование↔бой.** Над `Encounter` — `GameSession` (партия, часы, локация,
    флаги мира, общий `OngoingEffectTracker`/шина). `GameClock` — монотонное
    время в **раундах** (PHB-2024: раунд=6с, 1 мин=10 раундов, 1 ч=600). Бой
    двигает +1 раунд/раунд; исследование — по стоимости действия (переход
    локаций/обыск/отдых). Эффекты получают `duration` → `expires_at = now +
    длительность`; снятие по часам (граница раунда в бою И сдвиг часов в
    исследовании) — единый механизм, чтобы временные баффы (Bless 1 мин,
    концентрация до 10 мин) корректно истекали через границу мод. **Закрывает
    долг T2:** `OngoingEffectTracker` сейчас снимает только по событиям, без
    длительности/часов; концентрация без лимита времени.
  - **X1** локации + навигация (переход = время по часам) + триггер встречи →
    `Encounter` на той же партии/часах, возврат по `EncounterEnded`.
  - **X2** NPC + диалоги (дерево реплик; общение — отдельно, как обсуждали).
  - **X3** квесты + флаги мира + журнал.
  - **X4** skill-gated челленджи (проверки V) + скрытые объекты.
- **Y — Персистентность (приоритет 5, сквозное).** SQLite-справочники +
  `SaveService` (состояние в JSON-BLOB): сохранение созданных персонажей,
  прогресса и флагов мира, перебиндов хоткеев (отложено,
  `project_keybind_persistence_deferred`). Делать, когда есть что сохранять
  (после W/X).

Рекомендованный порядок: **U → V → W → X → Y** (каждый разблокирует следующий;
U даёт быстрый видимый результат на готовом фундаменте). Сеть и открытый мир
(разделы 10/13) — по-прежнему пост-MVP.

## Принципы прохождения

- **Каждый PR — вертикальный срез.** Никаких «отдельных PR на пустые классы».
- **Каждая новая фича сопровождается тестом по правилу из книги.** Маркер
  `pytest.mark.rules`.
- **Никаких «магических» решений.** Любое спорное место — отдельный ADR или
  пометка в `OPEN_QUESTIONS.md` до согласования.
- **MVP — это всё, что нужно для прохождения демо-сценария.** Всё остальное
  — пост-MVP.
